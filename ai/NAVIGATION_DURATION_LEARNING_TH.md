# ตัวเรียนที่รองรับเครดิตหลายก้าว

เพิ่ม `navigation_duration_dqn.py` เป็น schema ใหม่สำหรับ Double DQN ที่รับเครดิตจากช่วงไม่มีคำขอใหม่ ผ่าน targeted tests ใหม่ 18 รายการ โดยใช้ตัวอย่างซอฟต์แวร์เดิมที่บันทึกไว้และกรณีคำนวณสังเคราะห์ ไม่ได้เล่น R2 ซ้ำ ไม่ได้ฝึกจากการเดินเรือ และไม่เปิด validation/test หลักฐานอยู่ที่ `work/navigation-duration-preflight` และ `outputs/Warirak_Navigation_Duration_Learner_Audit.json`

## เป้าหมายการเรียนรู้

ถ้าคำขอจริงหนึ่งรายการกินเวลารวม d ก้าว เป้าหมายใช้ผลรวมรางวัลลดค่าตามเวลาที่บันทึกไว้ แล้วบวก `gamma^d × target_value` เฉพาะกรณียังไม่จบ episode ใช้ gamma=0.985 ต่อเวลาเดิม 100 มิลลิวินาที เลือก action ถัดไปจาก online network ภายใน mask แล้วอ่านค่าจาก target network ไม่ใช้ค่าของ action ที่ถูกห้าม

เมื่อชน เก็บได้ หรือหมดเวลาจำลองตามธรรมชาติ จะไม่มี bootstrap การขอความช่วยเหลือหรือเปลี่ยน epoch เพียงอย่างเดียวไม่ถือว่า episode จบ รางวัลสะสมไม่ถูกตัดให้เหลือขอบเขตหนึ่งก้าว ใช้ขอบเขตตรวจ `64 × (1−gamma^d)/(1−gamma)` ส่วนรางวัลดิบใช้ `64 × d` และเก็บแยกไว้เพื่อทบทวน ขอบเขตนี้เป็นขอบเขตอนุรักษนิยมจากสัญญารางวัล ไม่ใช่การรับรองว่าได้ตรวจทุก trajectory ของโลกจริง

คำขอที่ไม่เคยส่งยังคงเป็น null ในบันทึก ช่วง passive ก่อนคำขอแรกไม่มี action สำหรับสร้าง replay จึงต้องเก็บก้าว รางวัล และผลปลายทางใน episode journal โดยไม่สร้าง STOP สมมติขึ้น ตัวเรียนรับเฉพาะเครดิตที่ผูกกับคำขอจริงตามสัญญาของ bridge

## เวลา ประวัติ และข้อมูลที่เก็บ

รับ duration เป็นจำนวนเต็ม 1–960 โดยผลต่างเวลาภาพเดิมต้องเท่ากับ 100×d และผลต่าง record sequence ต้องเท่ากับ d ตรวจ discount ให้ตรงกับระยะเวลา ไม่เปลี่ยนเวลาในตัวอย่าง bridge เดิมและไม่แบ่งช่วงรอเป็น transition ที่ปลอมขึ้น

Canonical Node encoder ยังรับผิดชอบการตรวจ epoch ของแต่ละเฟรม หลังเปลี่ยน epoch หลายเฟรมใหม่อาจสะสมได้ระหว่างช่วงรอ ตัวเรียนจึงไม่บังคับว่าประวัติทั้งหมดต้องเป็นศูนย์ตลอดไป แต่ปฏิเสธเฟรมที่ยังย้อนถึงเวลาสถานะเริ่มต้นก่อนขอบเขต การตรวจนี้ไม่ใช่การยืนยันตัวตนของเครือข่าย และไม่ได้แทน sidecar/encoder ที่ตรวจแหล่งข้อมูลจริง

Replay จำกัด 8,192 รายการ เก็บเวกเตอร์ float32 พร้อมระยะเวลา discount และรางวัลดิบ float64 รวมถึงเวลา observation/encoding เดิม record, epoch และเหตุผล terminal ไม่มีพิกัดโลก ชนิดฉาก seed หรือค่ามอเตอร์ที่ใช้แทนความเร็วใน actor input สถาปัตยกรรมยังเป็น 234→64→64→7 บน CPU และใช้ Adam/loss/gradient clip/private RNG ตาม recipe เดิม

## Checkpoint และขอบเขตผลตรวจ

ใช้ model/checkpoint/recipe identity ใหม่ แยกจากตัวเรียนหนึ่งก้าว การโหลดผิดรุ่นถูกปฏิเสธ โดยคงไฟล์และผลรุ่นเก่าที่แช่แข็งไว้ การตรวจ network/Adam/RNG ใช้ตัวตรวจเดิมกับ replay ว่างที่แยกออกมาเท่านั้น ส่วน duration replay ตรวจด้วยกฎใหม่ ไม่เปลี่ยนข้อมูลหลายก้าวให้กลายเป็นข้อมูลหนึ่งก้าว

ตรวจการบันทึกและโหลดไฟล์แบบปลอดภัยแล้วทำสามขั้นถัดไป ได้ choices, sample indices, loss, network/target tensors, Adam, RNG และข้อมูล replay ตรงกันทุกค่าใน CPU runtime เดียวกัน ใช้กับ JournaledEpisodeCommitStore ได้ แต่ยังไม่มีการกู้ Node plant กลาง episode หรือการรับรองข้ามเวอร์ชัน/อุปกรณ์

กรณีสังเคราะห์มีระยะเวลา 2, 2, 4 และ 960 ก้าว เพื่อทดสอบคณิตศาสตร์และขอบเขต กรณี 960 ไม่ใช่ episode ที่วัดจากตัวจำลองจริง มี optimizer updates จำนวนจำกัดจากข้อมูลสังเคราะห์ใน unit tests เท่านั้น ไม่ใช่การฝึกโมเดลโครงงานหรือผลความแม่นยำ และไม่ได้รันชุดทดสอบเดิม/ทั้งโครงการซ้ำ

## คิวถัดไป

ทำ runtime Node/Python ที่ส่ง actor request, duration credit และ commit ระหว่าง episode ให้ครบ พร้อมตรวจการกู้ seed ที่ยังไม่ commit และสถานะ needs_repair ใช้ journal wrapper รักษาผลทุก episode โดยไม่ส่งเสริม orphan เป็นผลที่สำเร็จ Schedule ควรผูกกับตัวนับที่กู้ได้ เช่น choices และ replay.total_added และต้องกำหนดชัดเจนใน protocol ว่านับตาม decision หรือ physical step

ก่อนเริ่มฝึกจริงต้องแช่แข็งงบ schedule, snapshots, เกณฑ์ validation-only, ตัวอ้างอิงที่ใช้ข้อมูลเดียวกัน และ seed/exposure registry คง R2 current/inertia/noise/dropout/gain และ manual/watchdog/ACK/TTL เดิม แยก actuator delay 0/300/600 มิลลิวินาทีจาก inference wait ผลเวลาเสมือนไม่ใช่ Raspberry Pi FPS

รุ่นตรวจจับ public-v4 และนโยบายห้าคำขอบนเว็บยังคงเดิม ตรวจ D1 แบบอ่านอย่างเดียวแล้วตรง release.json ไม่มี deployment หรือการสั่งมอเตอร์จริงจากการตรวจส่วนนี้
