# ข้อมูลสังเกตสำหรับศึกษาการหลบล่วงหน้า

โมดูล `proactive_observation.mjs` สรุปข้อมูลจากตัวจำลอง R2 และเก็บอินพุตต้นฉบับให้ตรวจย้อนหลังได้ ใช้ schema ใหม่ `warirak.proactive-observation.v1` แยกจากนโยบาย R3 ข้อกำหนดอยู่ใน `proactive-observation-contract.json` โมดูลนี้เป็นส่วนเตรียมข้อมูล ยังไม่มีตัวเลือกการกระทำ นโยบายที่ฝึกแล้ว ตัวจับเวลา หรือการเชื่อมต่อมอเตอร์

## ผลตรวจหน้าต่างเหตุการณ์ที่มีอยู่

ตรวจไฟล์ `work/navigation-r3-postmortem/diagnostic.json` ที่บันทึกไว้แล้ว โดยแช่แข็งแผนและ hash ก่อนวิเคราะห์ ไม่เล่นฉากจำลองซ้ำและไม่เปิด validation/test ผลอยู่ใน `work/navigation-window-review/review.json`

เลือกทุกฉากในประเภทที่ชนหลังถูกจำกัดให้ STOP เพราะระยะต่ำกว่า 0.35 เมตร โดยไม่มีสถานะขอความช่วยเหลือก่อนจบ จึงได้ 11 หน้าต่างของนโยบายสุดท้าย และ 5 หน้าต่างของกฎที่ใช้ HOLD แต่ละหน้าต่างมีสิบ transitions ครอบคลุมหนึ่งวินาทีก่อนเหตุที่บันทึก

| ลักษณะที่ตรวจได้จากบันทึก | นโยบายสุดท้าย: 11 หน้าต่าง | กฎที่ใช้ HOLD: 5 หน้าต่าง |
| --- | ---: | ---: |
| มีแนวตรวจด้านหน้าต่ำกว่าเกณฑ์หยุด | 8 | 1 |
| มีแนวตรวจด้านข้างหรือด้านหลังต่ำกว่าเกณฑ์หยุด | 3 | 4 |
| เฉพาะแนวด้านข้าง/ด้านหลังต่ำกว่าเกณฑ์หยุด | 3 | 4 |
| คำขอก่อนเหตุทั้งสิบรายการเป็น STOP | 9 | 5 |

ตัวเลขนี้อธิบายหน้าต่างเหตุการณ์ที่เลือกไว้แล้ว ไม่ใช่คะแนนประเมินนโยบายใหม่ การมีคำขอ STOP ตลอดหนึ่งวินาทีไม่บอกโดยลำพังว่าทุกรายการเกิดจากนโยบายเลือกเองหรือจากข้อจำกัดของตัวกำกับ

พบข้อจำกัดของบันทึกเดิม: snapshot ย่อไม่ได้เก็บ target รวมถึง metadata เซนเซอร์ สถานะ armed/manual และแบตเตอรี่ครบ จึงสร้าง Q-feature และ action mask เดิมอย่างถูกต้องจากไฟล์นี้เพียงอย่างเดียวไม่ได้ ไม่มีการเติมค่าเหล่านี้จากการคาดเดา และยังพิสูจน์ปัญหาสถานะซ้ำที่ควรเลือกการกระทำต่างกันไม่ได้ การวิเคราะห์จึงบันทึกข้อจำกัดนี้ไว้ชัดเจน

## ข้อมูลที่โมดูลใหม่สรุป

`proactiveObservation(fullObservation, options)` รับแพ็กเก็ตเต็ม `warirak.mission-sim-observation.v2` ที่ระบุแหล่งข้อมูลเป็น simulation แล้วคืนข้อมูลต่อไปนี้

- ระยะทั้งแปดทิศและค่าต่ำสุดของกลุ่มด้านหน้า ซ้าย ขวา หลัง และรอบตัว เมื่อข้อมูลในกลุ่มไม่ครบ จะเป็น `null` แทนการเติมพื้นที่ว่าง
- ความเร็วตามยาว/ตามขวางที่แปลงกรอบจาก motion ที่วัดด้วยผลต่างตำแหน่ง และ heading ของ pose พร้อมเวลาและค่าความไม่แน่นอนเดิม ไม่มีการแปลงค่ามอเตอร์เป็นความเร็ว
- การฉายเวกเตอร์ความเร็วไปตามทิศของ ray เมื่อข้อมูลเวลาใกล้กันพอ ค่านี้ยังไม่ใช่ความเร็วระยะที่เปลี่ยนของผิววัตถุหรือเวลาที่จะชน และไม่รับรองช่องว่างระหว่าง ray
- สถานะ manual/disarmed/ขอความช่วยเหลือจากหลักฐานที่มี โดย `control_enabled` เป็น false เสมอ คำว่า `research_channel_armed` เป็นคำอธิบายสถานะอินพุต ไม่ใช่สิทธิ์สั่งมอเตอร์
- รายงาน ACK ที่จับคู่กับทะเบียนคำสั่งที่ออกจริงตาม sequence ค่าแรงขับ และเวลาเดิม แยกจากการวัดการเคลื่อนที่ทางกล
- ข้อมูล target ที่มีอยู่ พร้อมระบุว่าเวลาเป็นซองข้อมูลสังเกตสังเคราะห์ ยังไม่มีเวลาเก็บภาพกล้องที่ตรวจสอบแยกได้

ข้อมูลสังเกต ระยะ pose motion และ feedback ต้องไม่มาจากอนาคตและต้องมีอายุไม่เกิน 300 มิลลิวินาที การฉายข้อมูลร่วมต้องมีช่วงเวลาห่างกันไม่เกิน 100 มิลลิวินาที ค่าจากกรอบพิกัด วิธีวัด หรือการสอบเทียบที่ไม่ตรงข้อกำหนดจะเป็น unknown ข้อมูล cached ที่ไม่มีเฟรมใหม่ไม่กลายเป็นระยะสด

ค่าขอบเผื่อของการฉายความเร็วคำนวณจากค่าความไม่แน่นอนสังเคราะห์ที่ประกาศ เป็น engineering margin ที่ยังไม่มีการรับรอง coverage หรือการสอบเทียบฮาร์ดแวร์ ไม่ใช้ค่านี้เป็นหลักฐานยืนยันความปลอดภัย

## เวลา ACK และทะเบียนคำสั่ง

ทะเบียนใช้ `warirak.proactive-issued-control.v1` สูงสุด 16 รายการ แต่ละรายการต้องบันทึก `control_sequence`, `request_sequence`, `issued_at_ms`, `valid_until_ms`, `left` และ `right` จากคำสั่งที่ตัวจำลองออกจริง พร้อมแหล่ง simulation และหน่วย normalized อายุคำสั่งไม่เกิน 400 มิลลิวินาที ทะเบียนนี้เป็นหลักฐาน ไม่ส่งคำสั่งไปยังอุปกรณ์

ห้ามนำหมายเลขข้อเสนอที่เพิ่งคำนวณใหม่ไปจับคู่กับ ACK เก่าโดยไม่มีทะเบียนคำสั่งเดิม การจับคู่รายงานดิจิทัลไม่ยืนยันแรงขับทางกลหรือความเร็ว ส่วนรายงานแรงขับเป็นศูนย์ที่จับคู่ไม่ได้ก็ไม่ยืนยันว่าเรือหยุดนิ่ง

feedback ของตัวจำลอง R2 ประทับเวลาหลัง integration step จึงมีกรณีเวลา feedback เท่ากับเวลาหมดอายุ แม้คำสั่งถูกใช้ก่อนหน้านั้น โมดูลคงความหมายหลักฐานเดิมไว้ แต่แสดงว่าคำสั่งหมดอายุแล้วขณะประมวลผล ไม่มีการขยายอายุคำสั่ง ผลต่างเวลา feedback กับเวลาออกคำสั่งไม่ใช่ค่าความหน่วงขนส่งที่วัดได้โดยตรง

## เก็บหลักฐานเต็มเพื่อการทดลองถัดไป

`proactiveObservationRecord(fullObservation, options)` คืน features แยกจากสำเนา `original_observation` และ `original_issued_controls` บันทึกเต็มเป็นข้อมูลตรวจสอบ ส่วนผู้เรียนในอนาคตต้องอ่านเฉพาะ features ที่ protocol อนุญาต ไม่ใช้พิกัดโลกในส่วน diagnostic เป็นข้อมูลลับช่วยตัดสินใจ

ตัวอย่างการใช้กับแพ็กเก็ตเต็มจากตัวจำลอง:

```js
import {proactiveObservationRecord} from './proactive_observation.mjs';

const record = proactiveObservationRecord(fullObservation, {
  nowMs: processingTimeMs,
  issuedControls: originalIssuedControlLedger,
});
// บันทึก record ตามเวลาเดิม ผู้เรียกยังต้องจัดเก็บประวัติและตรวจลำดับเวลาเอง
```

โมดูลเป็น stateless จึงยังไม่ตรวจการใช้ sequence ซ้ำ การย้อนนาฬิกาข้ามแพ็กเก็ต หรือเก็บประวัติหลายเฟรมโดยอัตโนมัติ งานถัดไปคือ sidecar สำหรับบันทึกแพ็กเก็ตเต็ม/การตัดสินใจและทะเบียน issued control แบบจำกัดขนาด พร้อมการตรวจลำดับเวลา โดยรักษาฟิสิกส์และตัวกำกับ R2 เดิม ก่อนออกแบบนโยบายและแช่แข็ง protocol รอบใหม่

## การตรวจสอบ

ทดสอบเฉพาะส่วนใหม่ 17 รายการ ผ่านทั้งหมด ครอบคลุม motion ขาดหาย แรงขับเป็นศูนย์ขณะยังเคลื่อนที่ ระยะ cached/ไม่ครบ กรอบพิกัดผิด เวลาเก่า/อนาคต/เหลื่อมกัน manual/disarm/ขอความช่วยเหลือ ACK ไม่ตรงและเกินเวลา การเก็บอินพุตต้นฉบับ และการเชื่อมข้อมูลจาก fixture กระแสน้ำของ R2 ซอร์สและหลักฐานของรอบ R3 ยังตรง hash เดิม

ผลนี้ยืนยันพฤติกรรมของส่วนสรุปและบันทึกข้อมูล ยังไม่ได้วัดอัตราการเก็บขยะหรือการชนของนโยบายใหม่ ไม่มีการ deploy เว็บ เปลี่ยนทะเบียน D1 หรือเปิดมอเตอร์จริง
