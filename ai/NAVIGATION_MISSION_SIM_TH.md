# ตัวจำลองภารกิจ: STOP การลอยตามน้ำ และการติดค้าง

รุ่นพัฒนา `warirak-pool-mission-v4-dev` เพิ่มตัวควบคุมรักษาตำแหน่งแบบเขียนกฎใน **ตัวจำลองเท่านั้น** เพื่อทดสอบสมมติฐานก่อนฝึกนโยบายใหม่ ยังไม่มีนโยบาย AI ที่ฝึกสำหรับสภาพแวดล้อมนี้ ไม่มี adapter สำหรับเว็บไซต์หรือมอเตอร์ และยังไม่ได้กำหนด protocol การฝึก/validation/test ที่แช่แข็งแล้ว

โค้ดอยู่ที่ `navigation_mission_env.mjs` ข้อกำหนดอยู่ที่ `navigation-mission-v4-contract.json` ใช้ตรวจตัวอย่างได้จากรากโครงการ:

```sh
node ai/check_mission_simulation.mjs
node --test tests/navigation-mission.test.mjs
```

ตัวอย่างเป็นกรณีที่ผู้พัฒนากำหนดไว้เพื่อแยกตรวจตรรกะ มีการระบุ `fixture_used=true` ไม่ใช่ validation/test อิสระ และไม่ใช่ผลขับเรือจริง กรณีทดสอบบางรายการตัดเสียงรบกวนหรือสิ่งกีดขวางออกเพื่อแยกตรวจหน้าที่เฉพาะ ส่วนค่าปกติของสนามstressยังคงกระแสน้ำ ความคลาดเคลื่อนแรงขับ ความหน่วง ความคลาดเคลื่อนระยะ และข้อมูลขาดจากสนามv3

## สิ่งที่เปลี่ยนในตัวจำลอง

ใช้ตำแหน่งเริ่มต้น สิ่งกีดขวาง เป้าหมาย แรงขับคลาดเคลื่อน และกระแสน้ำจากตัวสร้างฉากv3เดิม โดยเก็บซอร์สv3ที่ใช้ในการทดลองก่อนหน้าไว้ตามเดิม เพิ่มช่วงเวลา100มิลลิวินาทีและการตอบสนองความเร็วลำเรือแบบอันดับหนึ่ง ค่าคงตัวเวลา0.35วินาทีเป็นสมมติฐานซอฟต์แวร์ที่ยังไม่ได้วัดจากเรือ

STOPทำให้คำสั่งมอเตอร์เป็นศูนย์และล้างคิวทันที แต่ยังคำนวณการเคลื่อนที่จากความเฉื่อยและกระแสน้ำ เรือจึงยังชนได้ในทุกโหมด ความหน่วงเดิม0/300/600มิลลิวินาทียังคงอยู่ หากความหน่วงเกินอายุคำสั่ง400มิลลิวินาที จะไม่ต่ออายุย้อนหลังเพื่อให้มอเตอร์ทำงาน

ข้อมูลตำแหน่ง ทิศหัวเรือ ความเร็ว และระยะรอบลำแปดทิศถูกเพิ่มเฉพาะการจำลอง มีแหล่งข้อมูล วิธีสร้าง หน่วย เวลา ความเชื่อมั่น และความไม่แน่นอนชัดเจน ความเร็วคำนวณจากการเปลี่ยนตำแหน่งจริงในโลกจำลองพร้อมเสียงรบกวนที่ประกาศไว้ ไม่ได้แปลงค่าคำสั่งมอเตอร์ให้กลายเป็นค่าความเร็วที่อ้างว่าวัดได้ การอ่านครั้งแรกยังไม่มีค่าความเร็ว ต้องมีการเคลื่อนเวลาของโลกก่อน

ข้อมูลเพิ่มเหล่านี้ทำให้ระบบมีการสังเกตมากกว่ารุ่นv3 จึงเปรียบตัวเลขข้ามรุ่นโดยตรงไม่ได้ แม้จะยังใช้ฉากและกระแสน้ำเดิม การเปรียบเทียบนโยบายครั้งต่อไปต้องให้baselineและcandidateใช้ข้อมูล ตัวกำกับ และฟิสิกส์เดียวกัน พร้อมแยกผลจากการเพิ่มเซนเซอร์ออกจากผลการเรียนรู้

## การกระทำและสถานะ

| การกระทำ | พฤติกรรม |
| --- | --- |
| STOP | คำสั่งแรงขับเป็นศูนย์ ล้างคิว ไม่ยืนยันว่าลำเรือหยุด |
| FORWARD / TURN_LEFT / TURN_RIGHT / PIVOT_LEFT / PIVOT_RIGHT | คำสั่งเดินเรือจำลองผ่านการตรวจด้านผู้ส่งและตัวรับ |
| HOLD | ใช้ข้อมูลตำแหน่งและความเร็วที่ผ่านการตรวจเพื่อรักษาตำแหน่งอ้างอิงด้วย feedback จำกัดแรงขับไม่เกิน±0.25 |
| RECOVERY_REQUEST | ตัดแรงขับและขอให้ผู้ใช้ประเมินการติดค้าง ยังไม่มีขั้นตอนขับถอยหรือแก้ติดค้างอัตโนมัติ |

HOLDต้องมีข้อมูลตำแหน่งและความเร็วใหม่ รวมถึงระยะรอบลำครบแปดทิศไม่น้อยกว่า0.65เมตร หากขาดหรือคุณภาพไม่พอ จะเป็น `HOLD_UNAVAILABLE` และรอการรีเซ็ต ไม่ถือว่าพื้นที่ด้านหลังว่างโดยอัตโนมัติ ตัวควบคุมนี้เป็น feedbackสังเคราะห์ที่ยังไม่ได้สอบเทียบแรงขับกับอุปกรณ์จริง

คำขอภารกิจมีsequenceของตนเอง ส่วนคำสั่งแรงขับในคิวและACKมีcontrol_sequenceแยกกัน ตัวรับตรวจเวลาและระยะในทิศที่จะเคลื่อนอีกครั้งก่อนใช้คำสั่ง ต้องมีACKตรงกับค่าคำสั่งที่ส่งจริงในตัวจำลอง ข้อมูลตอบรับขาดหรือไม่สอดคล้องเกิน500มิลลิวินาทีจะเป็น `ACTUATION_UNAVAILABLE` การตอบรับทางดิจิทัลไม่ใช่หลักฐานแรงขับทางกล

การควบคุมเองและการปลดการทำงานมีลำดับความสำคัญสูงกว่าHOLD ล้างคิว คำขอเดิม และตำแหน่งอ้างอิงทั้งหมด คำขอเดิมจึงไม่กลับมาทำงานหลังผู้ใช้ปล่อยการควบคุม ความผิดปกติและคำขอช่วยเหลือที่ค้างต้องรีเซ็ตอย่างชัดเจนขณะมีข้อมูลเซนเซอร์ใหม่และปลดการทำงานแล้ว หลังรีเซ็ตต้องส่งคำขอภารกิจใหม่

กรณีความเร็วต่ำต่อเนื่องอย่างน้อยสองวินาทีขณะมีACKเดินหน้าที่ตรงกัน จะขอประเมินการติดค้าง โดยไม่ใช้เงื่อนไขนี้กับHOLDหรือการหมุนอยู่กับที่ เพราะการรักษาตำแหน่งสำเร็จอาจมีแรงขับแต่ไม่ควรมีความเร็วเคลื่อนที่ เงื่อนไขนี้ยังตรวจการติดค้างไม่ได้ทุกกรณี เช่น กระแสน้ำอาจพาลำเรือที่ขับเคลื่อนไม่ได้ให้มีความเร็วอยู่

ยังมีข้อจำกัดที่ต้องแก้ก่อนฝึก: ค่า uncertaintyความเร็วเริ่มต้นของstressคือ0.008เมตร/วินาที ทำให้กรอบ `speed + 2 × uncertainty` ไม่ต่ำกว่าเกณฑ์ยืนยันความเร็วต่ำ0.015เมตร/วินาทีได้ แม้เรือจำลองจะติดค้าง กรณีjamที่ผ่านการตรวจในตัวอย่างจึงเป็นกรณีแยกที่ไม่มีเสียงรบกวน ต้องออกแบบสถานะขอช่วยเมื่อหลักฐานความก้าวหน้าไม่เพียงพอ โดยใช้ข้อมูลตำแหน่ง/การเคลื่อนที่ที่เป็นอิสระ แทนการลดความไม่แน่นอนหรือเดาว่าเรือหยุด

นอกจากนี้ ข้อมูลเซนเซอร์หายหนึ่งครั้งในรุ่นพัฒนานี้ทำให้สถานะfaultค้างตามกฎปัจจุบัน จึงยังไม่มีหลักฐานว่าทำภารกิจได้ต่อเนื่องเมื่อมีdropout การพัฒนาต่อควรตรวจความหมายของเวลารับข้อมูลและข้อมูลครั้งล่าสุดที่ยังไม่เก่าเกินเกณฑ์ รักษาเวลาเดิมของข้อมูล และทดสอบการหายต่อเนื่อง/การควบคุมเอง ก่อนกำหนดprotocol ไม่ฝึกเพื่อกลบปัญหาความพร้อมของข้อมูลเหล่านี้

## สิ่งที่ต้องทำก่อนรอบฝึก

ต้องกำหนดรูปแบบสถานะของผู้เรียนและโมเดลใหม่ ทำbaseline adapterที่ใช้ตัวกำกับและข้อมูลเพิ่มชุดเดียวกัน แล้วแช่แข็งสมมติฐาน ซอร์ส seed ชุดtrain/validation/test และเกณฑ์ก่อนเริ่มทดลอง เกณฑ์ต้องครอบคลุมอัตราชน ความสำเร็จ การหมดเวลา ความพร้อมของการควบคุม และกรณีfault พร้อมมีทั้งเพดานสัมบูรณ์และการเปรียบเทียบ ไม่เลือกโมเดลจากคะแนนtest

กรณีทดสอบที่เปิดดูแล้วทั้งหมดเป็นข้อมูลพัฒนา ไม่ใช้แทนการประเมินแบบแยกชุด และไม่อ้างว่าลดอัตราชน27.2%ของmemory-v3ได้แล้ว โมเดลตรวจจับpublic-v4 นโยบายเดิมบนเว็บไซต์ และตัวกำกับshadow/replayที่เผยแพร่ยังคงแยกจากตัวจำลองใหม่นี้
