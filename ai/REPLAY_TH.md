# เล่นบันทึกภาพและเซนเซอร์ซ้ำก่อนมีเรือ

เครื่องมือ `warirak_ai.replay` ตรวจข้อเสนอการเลี้ยวและการหยุดตามเวลาที่ข้อมูลเข้าระบบ โดยไม่เปิดกล้อง ไม่ต่อมอเตอร์ และไม่รอเวลาจริง เหมาะสำหรับตรวจภาพเก่า ช่วงข้อมูลขาด และความหน่วงก่อนทำชุดควบคุมจริง

## ทดลองจากตัวอย่างที่ให้มา

เปิด Terminal ในโฟลเดอร์โครงการ แล้วใช้:

```sh
cd ai
python -m warirak_ai.replay --input examples/paired-observations-simulation.jsonl --out runs/replay-demo-01 --thresholds ../frontend/assets/models/confidence-calibration-public-v4.json
```

ไฟล์ตัวอย่างสร้างขึ้นทั้งหมด มีภาพสังเกตจำลอง6รายการ รวมช่วงที่ข้อมูลหายและภาพที่เก่าเกินกำหนด **ไม่ใช่ข้อมูลจากกล้องหรือเซนเซอร์จริง** ทุกผลลัพธ์มี `control_enabled=false` เครื่องมือปฏิเสธโฟลเดอร์ผลลัพธ์ที่มีอยู่แล้วเพื่อรักษาหลักฐานเดิม หากทดลองซ้ำให้เปลี่ยนชื่อโฟลเดอร์

ผลลัพธ์ประกอบด้วย:

- `commands.jsonl`: ข้อเสนอที่เวลาแต่ละภาพเข้าระบบ และการเปลี่ยนสถานะจาก watchdog ระหว่างที่ไม่มีภาพใหม่ จบด้วย STOP เสมอ
- `report.json`: จำนวนข้อความ แหล่งข้อมูล อายุภาพเมื่อเข้าระบบ เหตุหยุด และช่วงเวลาที่มีข้อเสนอแรงขับไม่เป็นศูนย์ในนาฬิกาจำลอง
- `history.json`: ประวัติภาพสังเกตและคำสั่งล่าสุดสำหรับพัฒนานโยบายที่มีความจำต่อไป ยังไม่มีนโยบายความจำที่ฝึกเสร็จในเครื่องมือนี้

## รูปแบบบันทึกหนึ่งบรรทัด

แต่ละบรรทัดเป็น JSON ที่มี `schema="warirak.observation-pair.v1"`, `source="simulation"` หรือ `source="recorded"`, `received_at_ms`, `detection` และ `sensors` ตัวอย่างโครงสร้าง:

```json
{
  "schema": "warirak.observation-pair.v1",
  "source": "simulation",
  "received_at_ms": 1793188800100,
  "detection": {
    "schema": "warirak.detection.v1",
    "source": "detector",
    "frame_id": 1,
    "captured_at_ms": 1793188800000,
    "image_size": [640, 480],
    "detections": [{"class_id": 0, "confidence": 0.9, "xyxy": [300, 200, 340, 260]}]
  },
  "sensors": {
    "timestamp_unix_ms": 1793188800080,
    "battery_percent": 80,
    "clearance_m": [1.0, 1.0, 1.0],
    "armed": true,
    "manual_override": false
  }
}
```

ในไฟล์จริงให้แต่ละข้อความอยู่บรรทัดเดียวตามตัวอย่าง `.jsonl` ระยะเซนเซอร์เรียงซ้าย/หน้า/ขวา ใช้เมตร ตำแหน่งกรอบเป็นพิกเซล และเวลาเป็น Unix milliseconds

`received_at_ms` คือเวลาที่โปรแกรมผู้รับได้รับคู่ข้อมูล ใช้เป็นนาฬิกาสำหรับ replay ต้องเรียงตามเวลาที่มาถึงโดยไม่ย้อนกลับ ห้ามเปลี่ยน `captured_at_ms` หรือเวลาเซนเซอร์เป็นเวลาเล่นซ้ำเพื่อทำให้ข้อมูลดูใหม่ นาฬิกาของกล้อง เซนเซอร์ และผู้รับต้องอยู่บนฐานเวลาที่เทียบกันได้ เครื่องมือไม่เดาหรือแก้ความต่างของนาฬิกาให้

ใช้ `recorded` เมื่อเป็นบันทึกจากระบบจริงเท่านั้น โปรแกรมไม่ยอมรวม `simulation` กับ `recorded` ในการเล่นครั้งเดียว ภาพที่ไม่ผ่านการตรวจหรือข้อมูลเซนเซอร์ขาดจะนำไปสู่ STOP แทนการสร้างค่าทดแทน

## ขอบเขตของผล

watchdog ถูกเรียกในนาฬิกาจำลองทุก50มิลลิวินาทีระหว่างข้อความ โดยตรวจอายุคำสั่ง400มิลลิวินาทีและความสดเซนเซอร์ตาม `shadow_control` นี่เป็นการตรวจตรรกะโปรแกรม ไม่ใช่เวลาตอบสนองมอเตอร์ที่วัดจริง การใช้อุปกรณ์จริงยังต้องมีตัวรับและ watchdog บนฮาร์ดแวร์

อายุภาพที่รายงานครอบคลุมเวลาตั้งแต่อ่าน/จับภาพจนคู่ข้อมูลเข้าระบบ ไม่ใช่ FPS ของ Pi หรือความหน่วงกล้องที่วัดแยกแล้ว หากยังไม่มีป้ายกำกับอ้างอิง จะไม่รายงานความแม่นยำ อัตราเก็บสำเร็จ หรืออัตราชนจากบันทึกนี้ การตรวจพบขยะไม่ถูกนับเป็นเก็บสำเร็จ

รองรับไม่เกิน100,000ข้อความ ระยะเวลาไม่เกินหนึ่งชั่วโมง และไฟล์ไม่เกิน64MiB ต่อครั้ง หากมากกว่านี้ให้แบ่งบันทึกเป็นช่วงเพื่อรักษาขอบเขตการตรวจสอบ

## ตรวจคำขอหยุดเทียบกับข้อมูลการเคลื่อนที่และ ACK

เพิ่มโหมดตรวจสถานะภารกิจที่เปิดด้วย `--mission-monitor` โดยเฉพาะ โหมดปกติยังให้ข้อเสนอและรายงานตามเดิม ทดลองด้วยข้อมูลสังเคราะห์ที่ให้มา:

```sh
cd ai
python -m warirak_ai.replay --input examples/paired-mission-simulation.jsonl --out runs/replay-mission-01 --mission-monitor
python examples/check_replay_mission.py
```

ตัวอย่างมี12ข้อความ แสดงการขอSTOPแต่ยังเคลื่อนที่ การควบคุมเอง การรีเซ็ตขณะปลดการทำงาน หลักฐานความเร็วต่ำ และช่วงข้อมูลขาด **ทุกค่าถูกสร้างขึ้น ไม่ใช่บันทึกเรือจริง** ไฟล์ `mission.jsonl` แสดงผลตรวจแยกจาก `commands.jsonl` และ `report.json` มีส่วน `mission_monitor` เพิ่มขึ้น ไม่มีค่าความแม่นยำ อัตราชน หรือผลเก็บขยะเพิ่มจากโหมดนี้

ในคู่ข้อมูลเดิม เพิ่มฟิลด์ `mission_observation` ซึ่งมี `schema="warirak.mission-observation.v1"` และฟิลด์ทางเลือกต่อไปนี้:

| ฟิลด์ | ความหมาย |
| --- | --- |
| `observed_command` | ข้อเสนอคำสั่งเดิมที่บันทึกจริง รูปแบบ `warirak.shadow-command.v2` พร้อม sequence, issued/expiry และ environment เดิม ห้ามสร้างจากข้อเสนอใหม่ที่ replay คำนวณ |
| `motion` | ข้อมูล `warirak.motion-estimate.v1` มีเวลา หน่วยm/s กรอบอ้างอิงคงที่ วิธีวัด การสอบเทียบ ความเชื่อมั่น และความไม่แน่นอน ตาม `MISSION_MONITOR_TH.md` |
| `actuator_feedback` | ข้อมูล `warirak.actuator-feedback.v1` ที่ตอบรับ sequence ของ `observed_command` เดิม มีเวลาต้นทางและค่าแรงขับแบบ normalized การตอบรับทางดิจิทัลไม่ยืนยันแรงขับทางกล |
| `hold_requested` | Boolean แสดงคำขอรักษาตำแหน่ง ไม่ใช่คำสั่งเปิดตัวควบคุมHOLD ซึ่งยังไม่มี |
| `operator_reset` | Boolean สำหรับรีเซ็ตสถานะตรวจ ต้องมีเซนเซอร์ใหม่ที่ `armed=false` และส่งเป็นข้อความแยกจากข้อมูลคำสั่ง/motion/ACK ใหม่ |

ดูตัวอย่าง JSON ที่ครบใน `examples/paired-mission-simulation.jsonl` หากไม่มีฟิลด์ใดใน packet ใหม่ จะเก็บค่าครั้งก่อนพร้อม **เวลาเดิม** จนข้อมูลเก่าเกินกำหนด หากส่ง `null` จะล้างค่านั้น ไม่มีการสร้างความเร็วจากค่ามอเตอร์หรือสร้างACKให้ การไม่มี `observed_command` จะแสดง `WAIT_COMMAND` แม้ replay จะคำนวณข้อเสนอใหม่ได้แล้ว เพราะหมายเลขคำสั่งใหม่ไม่ใช่หลักฐานที่ใช้จับคู่ACKเก่า

เมื่อ `source="recorded"` ต้องใช้ `motion.source="measured"` กับวิธีวัดที่รองรับ และ `actuator_feedback.source="controller_feedback"` ข้อมูลจำลองที่ติดป้ายผิดจะไม่ถูกยอมรับเป็นหลักฐานวัดจริง นาฬิกาทุกฟิลด์ต้องเทียบกับ `received_at_ms` ได้ ไม่มีการเลื่อนเวลาหรือแก้หมายเลขsequenceเพื่อให้ผ่าน

ตัวตรวจใช้เวลาเสมือนเดียวกับ replay และถูกเรียกทุกช่วงwatchdogด้วย ข้อมูลmotionเดิมที่อ่านซ้ำไม่เพิ่มจำนวนหลักฐาน ข้อมูลขาด ความไม่แน่นอนสูง หรือACKไม่ตรงจะไม่กลายเป็นคำยืนยันว่าเรือหยุด สถานะHOLD/RECOVERY/ความผิดปกติจะค้างจนมีการรีเซ็ตที่ถูกต้อง การควบคุมเองและการปลดการทำงานล้างคำสั่ง/ACKที่แคชไว้ ต้องมีข้อเสนอเดิมที่บันทึกใหม่ก่อนตรวจการเดินหน้าต่อ

ผลนี้เป็น **การประเมินประกอบการวิเคราะห์** ยังไม่แก้หรือห้ามข้อเสนอใน `commands.jsonl` ไม่ใช่ตัวควบคุมรักษาตำแหน่งหรือกู้การติดค้าง และไม่ได้ลดอัตราชน27.2%ของการทดลองmemory-v3 การจบบันทึกทำให้ข้อเสนอreplayเป็นSTOP แต่ไม่ยืนยันว่าตัวรับมอเตอร์ตอบรับSTOPหรือเรือหยุดจริง ส่วน `receiver_stop_at_end_confirmed` จึงเป็นfalseเสมอ ค่าขีดจำกัดเวลาและความเร็วในรายงานเป็นค่าเริ่มต้นซอฟต์แวร์ ยังไม่ได้สอบเทียบกับฮาร์ดแวร์
