# แผนพัฒนา AI วารีรักษ์ต่อเนื่อง

ผู้ใช้อนุญาตให้ฝึกและพัฒนาต่อเมื่อ 28 ตุลาคม 2569 และยืนยันว่า **ยังไม่ได้ประกอบเรือ ให้พัฒนาซอฟต์แวร์และฝึกก่อน** จึงไม่มีการอ้างว่าได้ทดสอบขับเรือจริง

## การตรวจจับ: public-v4

เริ่มจากน้ำหนัก public-v2 ที่เผยแพร่ ใช้ชุดข้อมูล public-v3 เดิม 1,715 ภาพ โดยไม่สร้างจำนวนภาพเพิ่มจากการทำซ้ำ แบ่ง train 1,426 / validation 147 / test 142 ภาพ ตาม manifest เดิม

เหตุผลของรอบนี้: public-v3 เพิ่มภาพขวด แต่ผลฝาขวดลดลง จึงทดลองเพิ่มน้ำหนักคลาสตามความถี่ (`cls_pw=0.5`) และลด learning rate เป็น 0.00008 ฝึกสูงสุด 45 รอบ หยุดเมื่อ validation ไม่ดีขึ้น 12 รอบ ใช้ภาพ 800 พิกเซล batch 8 และ seed 61 เก็บ best/last checkpoint ไว้ต่อจากจุดค้างได้

เกณฑ์ก่อนฝึก: validation mAP50–95 ต้องเพิ่มอย่างน้อย 0.003 และแต่ละคลาสลดไม่เกิน 0.02 จึงจะพิจารณาเผยแพร่ ต้องตรวจ calibration และ NCNN ด้วย ชุด validation ถูกใช้แล้วหลายรอบ และ test เดิมเคยเปิดผลแล้ว ห้ามใช้ test เลือกโมเดลหรืออ้างเป็นผลอิสระใหม่ รอบนี้ฝึกจริง27รอบและผ่านเกณฑ์แล้ว: ค่าเฉลี่ยvalidation38.32%→39.08% ขวด37.16%→39.20% ฝาขวด39.48%→38.96% จึงเผยแพร่public-v4-2026-10-28หลังตรวจNCNNและไฟล์ครบ โดยเก็บpublic-v2เดิมไว้อ้างอิง

อ้างอิงการถ่วงน้ำหนักคลาส: [Ultralytics Train](https://docs.ultralytics.com/modes/train/#train-settings)

## การเดินเรือ: ทดสอบความคลาดเคลื่อน

เพิ่มสนาม stress-v2: แรงขับคลาดเคลื่อน ±20%, กระแสน้ำ ±0.08 เมตร/วินาที, หน่วงคำสั่ง 0–0.6 วินาที, มุมเป้าหมายคลาดเคลื่อน ±0.16 เรเดียน, ระยะเป้าหมาย ±0.25 เมตร, ระยะเซนเซอร์ ±0.1 เมตร และเป้าหมายหายจากภาพ 8% ตัวเลขเป็นค่าทดลองในตัวจำลอง ไม่ใช่ค่าที่วัดจากเรือ

ฝึกเพิ่มจากนโยบายเดิม 12,000 และ 20,000 รอบ แล้วเทียบ validation กับรุ่นเดิมโดยใช้สนามเดียวกัน ต้องดีขึ้นในสนามยากและรักษาผลในสนามปกติ จึงจะเปิดผลสนาม test ใหม่ ผลชุดนี้ไม่ผ่านเกณฑ์ จึงไม่แทนที่นโยบายบนเว็บ และยังไม่เปิดสนาม test ใหม่

ข้อค้นพบ: Q-table ที่ใช้ภาพสังเกตปัจจุบันอย่างเดียวไม่รับประกันผลเมื่อคำสั่งหน่วงและภาพขาดช่วง ขั้นถัดไปควรเพิ่มความจำของคำสั่ง/ภาพและคำสั่งหยุดที่ชัดเจน พร้อมแยกตัวกำกับความปลอดภัยจากนโยบายที่เรียนรู้ การเพิ่มจำนวนรอบอย่างเดียวไม่ใช่คำตอบ

## จากผลตรวจจับไปสู่คำสั่งเลี้ยว

`warirak_ai.visual_pilot` รับข้อความผลตรวจจับจาก `infer.py` คู่กับข้อมูลเซนเซอร์ แล้วออกข้อเสนอคำสั่งซ้าย/ขวาเท่านั้น ยืนยันเป้าหมายอย่างน้อยสามภาพต่อเนื่อง ห้ามใช้ภาพซ้ำเป็นหลักฐานเพิ่ม หยุดเมื่อภาพ/เซนเซอร์เก่า แบตเตอรี่ต่ำ มีสิ่งกีดขวาง หรือผู้ใช้ควบคุมเอง

ใช้ตำแหน่งแนวนอนในภาพเพื่อเสนอทิศเลี้ยว ไม่เดาระยะเป็นเมตรจากขนาดขวด ข้อมูลจับภาพแยกจากเวลาประมวลผลเสร็จ การตรวจพบขยะไม่นับว่าเก็บสำเร็จ ข้อเสนอยังมี `control_enabled=false` และไม่มี GPIO/serial/motor transport

ลองกับบันทึก JSONL ที่แต่ละบรรทัดมี `detection` และ `sensors`:

```sh
cd ai
python -m warirak_ai.visual_pilot --observations paired-observations.jsonl
```

เมื่อประกอบเรือแล้ว ต้องระบุรุ่นกล้อง บอร์ดขับมอเตอร์ ขั้ว/ทิศหมุน ขาควบคุม และเซนเซอร์จริง ก่อนทำ adapter ที่มี watchdog และตรวจบนแท่น ต่อด้วยทดสอบในน้ำโดยมีผู้ดูแล พร้อมเก็บวิดีโอจากกล้องเรือเพื่อทำชุดประเมินอิสระ

## ตัวกำกับการหยุดและประวัติคำสั่ง

เพิ่ม `warirak_ai.shadow_control` เป็นข้อกำหนดรุ่นใหม่ `warirak.shadow-command.v2` แยกจาก Q-table เดิม มีคำสั่ง `STOP` ชัดเจนและเก็บประวัติภาพสังเกตกับคำสั่งย้อนหลังแบบจำกัดจำนวน ข้อมูลนี้เป็นโครงสร้างสำหรับพัฒนานโยบายที่มีความจำต่อไป **ส่วนเก็บประวัตินี้ไม่ใช่นโยบายที่ฝึกแล้ว** นโยบายทดลองที่ใช้ประวัติถูกฝึกแยกในรอบmemory-v3 ซึ่งสรุปไว้ท้ายเอกสารและยังไม่ใช้ควบคุมบนเว็บ

`ShadowSupervisor` ตรวจเซนเซอร์ แบตเตอรี่ การควบคุมเอง ระยะปลอดภัย ความสด ลำดับเวลา และขอบเขตแรงขับอีกครั้งอย่างเป็นอิสระ หากไม่ได้รับคำสั่งใหม่ภายใน 400 มิลลิวินาที เมธอด `tick()` จะคืน STOP เมื่อพบเหตุหยุด จะยกเลิกคำสั่งก่อนหน้าและไม่คืนการเคลื่อนที่เดิมเพียงเพราะสิ่งกีดขวางหายไป ต้องมีข้อเสนอใหม่ที่ผ่านการตรวจ

โปรแกรมผู้เรียกต้องเรียก `tick()` ต่อเนื่องเพื่อใช้กลไกตรวจเวลานี้ ส่วนนี้ไม่มี timer ที่ทำงานเอง ไม่มีการต่อ serial/GPIO และไม่ใช่ watchdog ทางไฟฟ้าของมอเตอร์ ตัวรับบน ESP32 และการสอบเทียบกับอุปกรณ์ยังเป็นงานภายหลัง

การยืนยันเป้าหมายจะเริ่มใหม่หากช่วงห่างระหว่างภาพนานเกินกำหนด จึงไม่รวมภาพที่อยู่ห่างกันเป็นหลักฐานต่อเนื่องโดยอัตโนมัติ

## ทำงานต่อแต่ละรอบ

เพิ่มเครื่องมือเล่นบันทึกภาพ/เซนเซอร์ซ้ำตามเวลาที่ข้อมูลเข้าระบบแล้ว อ่าน `REPLAY_TH.md` มีตัวอย่างสังเคราะห์ที่ระบุแหล่งข้อมูลชัดเจน ตรวจช่วงข้อมูลขาดและภาพเก่าโดยไม่ปรับเวลาให้ดูใหม่ ผลจากเครื่องมือนี้เป็นข้อเสนอในนาฬิกาจำลอง ไม่ใช่ความแม่นยำหรือผลขับเรือจริง

งานฝึกบนเครื่องมีสถานะและ checkpoint งานติดตามอ่านสถานะก่อนเสมอและไม่ฝึกซ้ำขณะ process ปกติ รอบที่ไม่ผ่านจะเก็บผลตามจริงและคงโมเดลที่เผยแพร่ งานถัดไปต้องมีสมมติฐานหรือข้อมูลใหม่พร้อม protocol ก่อนฝึก ไม่วนเพิ่ม epochs อย่างไม่มีจุดหมาย และไม่ใช้บริการ GPU ที่มีค่าใช้จ่ายโดยอัตโนมัติ

ระหว่างรอเรือ สามารถพัฒนาตัวกำกับการหยุด การบันทึกข้อมูล การประเมินความหน่วง การติดตามเป้าหมาย และทดสอบกับข้อมูลสาธารณะต่อได้ ความสำเร็จในตัวจำลองแยกจากความสำเร็จกับเรือจริงเสมอ

## ผลทดลองความจำคำสั่งและ STOP

เพิ่มส่วนตรวจสถานะ `mission_monitor` เพื่อแยกคำขอSTOP รายงานจากตัวรับมอเตอร์ และหลักฐานความเร็วออกจากกันแล้ว มีสถานะขอHOLD/RECOVERY/ผู้ใช้ช่วยพร้อมกรณีทดสอบสังเคราะห์ ดู `MISSION_MONITOR_TH.md` ส่วนนี้ยังไม่มีตัวควบคุมรักษาตำแหน่ง ไม่ลดอัตราชนของmemory-v3 และไม่ต่อมอเตอร์จริง

เชื่อมตัวตรวจนี้กับ `replay --mission-monitor` แล้ว ใช้ข้อเสนอคำสั่งเดิมที่บันทึกเพื่อจับคู่ACK แยกจากหมายเลขคำสั่งที่replayคำนวณใหม่ เก็บเวลาmotion/ACKเดิม ตรวจข้อมูลขาดและข้อมูลซ้ำตามนาฬิกาเสมือน มีตัวอย่างการควบคุมเองและรีเซ็ตขณะปลดการทำงาน ดู `REPLAY_TH.md` ผลเป็นการวิเคราะห์ประกอบ ยังไม่แทรกแซงข้อเสนอแรงขับและไม่ยืนยันว่าเรือหยุดจริง

สภาพแวดล้อม memory-v3 และschemaนโยบายใหม่ทำแล้ว ฝึก16,000/40,000รอบจากprotocolที่กำหนดก่อนเริ่ม ผู้สมัคร40,000รอบผ่านเกณฑ์เปรียบเทียบvalidation แต่ยังไม่แทนนโยบายบนเว็บ: testสังเคราะห์สนามยากสำเร็จ67.9%และชน27.2% ตรวจตัวอย่างvalidationพบการลอยตามกระแสน้ำขณะSTOP จึงต้องแก้การรักษาตำแหน่ง/การติดค้างและสถานะกำกับก่อนฝึกต่อ รายงานเต็มที่ `NAVIGATION_MEMORY_TH.md` ตัวอย่างนี้ไม่ใช่ผลเรือจริงและไม่ได้เปลี่ยนโมเดลตรวจจับpublic-v4


## รอบวิจัยการเดินเรือ R2

เริ่มรอบCPUในเครื่องที่ `work/navigation-mission-r2-experiment` หลังทดสอบซอฟต์แวร์ผ่าน99รายการและบันทึกprotocolพร้อมhashก่อนฝึก ใช้sparse Q-learningหนึ่งเส้นทางสูงสุด6,000episodes พร้อมcheckpointทุก100episodes เลือกจากvalidationเท่านั้น และตัวรันยังไม่เปิดtestอัตโนมัติ ดู `NAVIGATION_MISSION_LEARNING_TH.md`

เมื่อprocessNodeของรอบนี้ยังปกติ ห้ามเริ่มงานฝึกหรือประเมินซ้ำ แม้ไม่มีPythonหรือGPUทำงาน หลังขอความช่วยเหลือยังคำนวณการลอยจนจบepisodeและอยู่ในตัวหาร ไม่มีการควบคุมเรือจริงหรืออัปเดตนโยบายบนเว็บจากการเริ่มรอบนี้


รอบR2ฝึกครบ6,000episodesและทบทวนแล้วแบบ `retained_baseline`: ผู้สมัคร2,000/6,000ไม่ผ่านvalidation จึงไม่เปิดtestและไม่เผยแพร่นโยบายใหม่ ผู้สมัคร6,000เก็บสำเร็จ32%/15%และชน26.5%/70%ในvalidationจำลองปกติ/ยาก200episodesต่อสนาม อ่าน `NAVIGATION_MISSION_R2_RESULT_TH.md` ห้ามเพิ่มรอบสูตรเดิมหรือresumeงานนี้อีก ขั้นถัดไปเป็นpostmortemแบบจำกัดจากหลักฐานที่มี ไม่ใช่การฝึกซ้ำ


## แยกเจ้าของคำขอและรอบNavigation-only R3

ทำpostmortemแบบจำกัดบนฉากที่เคยฝึกแล้ว โดยไม่มีQupdatesหรือvalidation/testใหม่ พบกลไกการสำรวจเลือกRECOVERY_REQUESTโดยตรงในตัวอย่าง จึงเริ่มสมมติฐานใหม่แยกเจ็ดคำขอเดินเรือของAIจากคำขอoperator โดยรักษาตัวกำกับR2ครบ ดู `NAVIGATION_ACTION_OWNERSHIP_TH.md`

รอบใหม่ `work/navigation-only-r3-experiment` ใช้NodeCPUหนึ่งprocessสูงสุด6,000episodesและเกณฑ์เท่ากับR2ทุกค่า แผน/hashแช่แข็งก่อนฝึก ใช้seedใหม่และยังไม่เปิดtest ห้ามเริ่มงานซ้ำขณะprocessปกติ รอบR2เดิมยังปิดแบบretained_baselineและไม่ถูกแก้ไข ไม่มีการเผยแพร่หรือควบคุมมอเตอร์จริงจากการเริ่มรอบนี้


## ผล Navigation-only R3 และคิวหลบล่วงหน้า

รอบ R3 ฝึกครบ 6,000 episodes และปิดแบบ `retained_baseline` โดย `review_complete` และ `delivery_complete` เป็น true ผู้สมัครทั้งสองไม่ผ่านเกณฑ์ validation ไม่มีการเปิด test หรือเปลี่ยนนโยบายบนเว็บ ผู้สมัครสุดท้ายเก็บสำเร็จ 38.5%/22% และชน 32.5%/70.5% ในสนามจำลองปกติ/ยาก จำนวน 200 ฉากต่อสนาม อ่าน `NAVIGATION_ONLY_R3_RESULT_TH.md` ห้าม resume ฝึกเพิ่ม หรือเล่น validation ของรอบนี้ซ้ำ

วิเคราะห์แบบจำกัดจากฉากฝึกเดิม 24 ฉากต่อผู้ควบคุมแล้ว พบตัวอย่างการชนหลังคำสั่งแรงขับเป็นศูนย์และหลังขอความช่วยเหลือ โดยยังคำนวณกระแสน้ำ/ความเฉื่อยต่อ ข้อมูลนี้ไม่ใช่สัดส่วนสาเหตุของการชนทั้งหมด ไม่ใช่ผลเรือจริง และไม่เปิด validation/test เพิ่ม หลักฐานอยู่ที่ `work/navigation-r3-postmortem` ห้ามรันซ้ำ

ขั้นต่อไปตาม `NAVIGATION_PROACTIVE_AVOIDANCE_PLAN_TH.md` คือดูหน้าต่างเหตุการณ์ที่บันทึกแล้วและออกแบบข้อมูลสังเกตสำหรับการหลบก่อนเข้าเขตหยุด พร้อม deterministic fault tests ก่อนแช่แข็ง protocol ใหม่ ยังไม่ได้ฝึกนโยบายดังกล่าว ห้ามลดตัวกำกับ เปลี่ยนเวลาให้ดูสด สร้างความเร็วจากแรงขับ หรือตัดฉากความหน่วงที่ควบคุมไม่ได้ออกจากคะแนน งานติดตามยังดำเนินต่อโดยไม่มีงานฝึกซ้ำที่กำลังรัน


## ส่วนข้อมูลสังเกตสำหรับการหลบล่วงหน้า

ตรวจหน้าต่างเหตุการณ์เดิมแล้วโดยไม่มี rollout หรือการฝึกเพิ่ม พบว่าบันทึกย่อขาด target และ metadata เซนเซอร์ครบ จึงไม่สามารถสร้าง Q-feature/action mask เดิมได้อย่างถูกต้อง และไม่เติมข้อมูลจากการคาดเดา ผลตรวจอยู่ใน `work/navigation-window-review` และปิดงานส่วนนี้แล้ว

เพิ่ม `proactive_observation.mjs` เป็น schema ใหม่สำหรับสรุประยะรอบตัว ความเร็วตามยาว/ตามขวางที่วัดอย่างอิสระ เวลาเดิม และการจับคู่ ACK กับ issued control พร้อมบันทึกแพ็กเก็ตเต็ม ส่วนใหม่ผ่าน deterministic tests 17 รายการ อ่าน `PROACTIVE_OBSERVATION_TH.md` และ audit `outputs/Warirak_Proactive_Observation_Audit.json` ยังไม่มีนโยบาย การตรวจ sequence ข้ามเฟรม ตัวจับเวลา หรือการสั่งมอเตอร์ และยังไม่พร้อมเริ่มฝึก

งานถัดไปเป็น sidecar เก็บประวัติแบบจำกัดขนาดและตรวจลำดับเวลา/sequence จากข้อมูลเต็มรอบตัวจำลอง R2 ที่คงเดิม ก่อนกำหนดนโยบายและ protocol ใหม่ ไม่เล่นรอบ R2/R3 หรือหน้าต่างที่ตรวจเสร็จซ้ำ ไม่มีการ deploy เว็บหรือเปลี่ยนโมเดลที่เผยแพร่


## ส่วนบันทึกประวัติแบบจำกัดขนาด

เพิ่ม `proactive_sidecar.mjs` และตัวหุ้มตัวจำลอง `proactive_sidecar_r2.mjs` แล้ว ผ่าน deterministic tests เฉพาะส่วนใหม่ 26 รายการ เก็บแพ็กเก็ตเต็ม คำขอต้นฉบับ และ issued/applied control จากตัวจำลอง พร้อมตรวจข้อมูลซ้ำ/ขัดแย้ง เวลา/sequence ไหลย้อน และประวัติที่จำกัดขนาด อ่าน `PROACTIVE_SIDECAR_TH.md` และ audit `outputs/Warirak_Proactive_Sidecar_Audit.json` งานส่วนนี้ปิดแบบ review_complete/delivery_complete แล้ว

ส่วนบันทึกไม่สร้างคำสั่งและไม่ควบคุมการเคลื่อนที่ เมธอด cancel ยกเลิกเฉพาะบริบทการบันทึก ไม่ส่ง STOP ส่วนตัวหุ้มส่งคำขอเดิมให้ R2 โดยไม่เปลี่ยนฟิสิกส์หรือตัวกำกับ ผลตรวจ snapshot เทียบกับตัวจำลองเดิมตรงกันในกรณีทดสอบ ไม่มีการควบคุมมอเตอร์จริง

ตรวจทะเบียน D1 แบบอ่านอย่างเดียวแล้ว รุ่น active ยังตรง release.json คือ public-v4-2026-10-28 ไม่มีการเขียนข้อมูลหรือ deploy ขั้นถัดไปคือออกแบบตัวเสนอการหลบล่วงหน้าและแผนกรณีพัฒนาที่จำกัดพร้อม hash ก่อนทดลอง ยังไม่มีนโยบายใหม่และยังไม่เริ่มฝึกหรือเปิด validation/test


## ผลพัฒนาตัวเสนอการหลบล่วงหน้า v1

เพิ่มตัวเสนอแบบใช้กฎที่ยังไม่ผ่านการฝึก และแช่แข็งแผน/source hash ก่อนทดสอบ ผ่าน unit tests 20 รายการหลังแก้เฉพาะกรณีทดสอบนาฬิกาโดยเก็บ revision เดิมไว้ครบ รันฉากพัฒนาแบบเจาะจง 14 ฉากต่อตัวควบคุมจบแล้ว ผลใหม่เก็บได้ 9 ชน 5 เทียบกับกฎอ้างอิงเก็บ 8 ชน 6 แต่มีฉากสิ่งกีดขวางด้านข้างที่แย่ลง ผลไม่ใช่ validation/test หรือความแม่นยำภาคสนาม

แม้ผ่านเกณฑ์ขั้นพัฒนาที่กำหนดไว้ การทบทวนไม่อนุมัติให้ใช้ต่อหรือเริ่มฝึก เพราะพบ sidecar v1 ปฏิเสธเฟรม cached ที่ metadata เพิ่มตามลำดับแต่ยังไม่เคยอ่าน งานนี้ปิดแบบ reviewed_not_promoted, review_complete/delivery_complete=true ที่ `work/proactive-selector-v1-dev-r1` รายงาน `PROACTIVE_SELECTOR_V1_RESULT_TH.md` ห้ามเล่นฉากเดิมซ้ำหรือแก้ไฟล์ที่แช่แข็งย้อนหลัง

คิวถัดไปคือ sidecar schema/ซอร์สรุ่นใหม่ พร้อม regression tests สำหรับข้อมูลแคชที่ยังไม่เคยเห็น โดยต้องคง cached เป็น unknown ไม่ปลอมความสดและไม่ลดตัวกำกับ จากนั้นตรวจหน้าต่างฉากด้านข้างที่เก็บไว้และข้อจำกัดข้อมูลก่อนกำหนดสมมติฐาน/แผนใหม่ ไม่มีการฝึก เปิด validation/test เปลี่ยนโมเดลเว็บ หรือสั่งมอเตอร์จริง ทะเบียน D1 อ่านอย่างเดียวแล้วยังตรง public-v4


## แก้ข้อมูลแคชใน sidecar v2

แยก source/schema sidecar v2 เพื่อรับ metadata ของเฟรม cached ที่เพิ่มตามลำดับแต่ยังไม่เคยเห็นขณะสด โดยค่าระยะยังเป็น unknown และไม่นับเป็นหลักฐานเฟรมสด ผ่าน targeted checks 40 รายการ พร้อมเทียบกับ R2 ที่ไม่เปลี่ยนฟิสิกส์/ตัวกำกับ รายงาน `PROACTIVE_SIDECAR_V2_TH.md` และ audit `outputs/Warirak_Proactive_Sidecar_v2_Repair_Audit.json` งานซ่อมปิดแบบ review_complete/delivery_complete แล้ว ซอร์สและผล v1 คงเดิม

ตรวจหน้าต่างข้อมูลด้านข้างเดิมโดยไม่มี rollout เพิ่มแล้ว พบ 10 เฟรมที่ FORWARD อยู่ใน mask แต่กฎ v1 ขอ STOP เพราะ pivot/HOLD ไม่พร้อม ข้อมูลนี้ไม่พิสูจน์ว่า FORWARD ปลอดภัยทั่วไป และขาดเฟรมเริ่มต้นก่อน step21 ผลการทดลอง v1 ยังไม่อนุมัติและไม่มีคะแนนใหม่

ขั้นถัดไปคือสมมติฐานจัดลำดับคำขอที่ยังได้รับอนุญาต พร้อมแผนกรณีพัฒนาใหม่ที่แยกสิ่งกีดขวางด้านข้างแบบมีขอบเขตออกจากผนังยาว ก่อนทดลองหรือฝึก ห้ามเลือก FORWARD เหมารวม ผ่อนตัวกำกับ หรือปรับ threshold วนบนฉากเดิม ไม่มีการเปิด validation/test เปลี่ยนรุ่นเว็บ หรือสั่งมอเตอร์จริง ทะเบียน D1 อ่านอย่างเดียวแล้วยังตรง public-v4


## ผลกฎ corridor และแผน encoder สำหรับการเรียนรู้

ทดสอบกฎ conditional FORWARD รุ่น selector-v2 ในชุดพัฒนาใหม่ 10 คู่เรขาคณิต รวม 20 ฉากต่อตัวควบคุม โดยใช้ sidecar-v2 เหมือนกันทั้งคู่ แช่แข็งแผน/source ก่อนรันและผ่าน preflight 18 รายการ ผลผู้สมัครเก็บได้ 5 ชน 15 เทียบกับ v1 ที่เก็บ 0 ชน 20 ในชุดที่เจาะจงข้อจำกัดนี้ ผลดีขึ้นเฉพาะ 5 ฉากวงกลมด้านข้าง ไม่ใช้ extension ในฉากผนัง แต่ผนังทั้งสิบฉากยังชน ไม่ใช่ความพร้อมภาคสนามหรือข้อพิสูจน์ว่าดีกว่าตัวอ้างอิงที่แข็งแรงที่สุด

งานปิดแบบ reviewed_development_evidence_only, review_complete/delivery_complete=true ที่ `work/corridor-selector-v2-dev` ห้ามเล่นซ้ำหรือปรับ threshold บนชุดนี้ รายงาน `CORRIDOR_SELECTOR_V2_RESULT_TH.md` และ audit `outputs/Warirak_Corridor_Selector_v2_Outcome_Audit.json` ยังไม่มีโมเดลที่ฝึกใหม่ การเปิด validation/test หรือ deployment

คิวต่อไปตาม `NAVIGATION_LEARNING_NEXT_DESIGN_TH.md` คือ schema/encoder สำหรับ features ต่อเนื่องพร้อมประวัติและ known/time masks แล้วตรวจสะพานข้อมูลก่อนแช่แข็ง protocol การเรียนรู้ใหม่ ไม่เลียนแบบกฎที่ยังชนเป็นคำตอบจริงทุกกรณี ไม่เพิ่ม epochs ของโมเดลเดิม และไม่อ้าง virtual-time inference เป็นความหน่วงบน Raspberry Pi จริง


## Encoder ประวัติและสัญญาข้อมูล Node/Python

เพิ่ม encoder สำหรับประวัติสามเฟรม รวม 234 ค่า โดยแยกข้อมูลขาดจากค่าศูนย์ที่วัดได้ ใช้เวลาและ epoch เดิม ไม่ใส่พิกัดโลกหรือคำตอบที่เลือกให้เฟรมปัจจุบัน เพิ่มสัญญาคำขอ/คำตอบที่ตรวจ action mask, digest, deadline, cancel และ replay ผ่าน targeted tests 26 รายการตาม protocol ที่แช่แข็งก่อนทดสอบ รายงาน `NAVIGATION_HISTORY_ENCODER_TH.md` และ audit `outputs/Warirak_Navigation_History_Encoder_Audit.json`

งานส่วนนี้ปิดแบบ review_complete/delivery_complete แล้ว Python ที่ใช้ตรวจเป็น masked-argmax fixture อย่างชัดเจน ไม่ได้โหลดหรือฝึกโมเดล ไม่มี rollout หรือ validation/test ใหม่ การส่งข้อมูลตรงกันไม่ใช่ผลความแม่นยำหรือความหน่วง Raspberry Pi และยังไม่มี masked learning targets หรือ checkpoint ระบบเรียนรู้

คิวถัดไปเป็นสถาปัตยกรรมการเรียนรู้ขนาดเล็ก การทดสอบ action-mask targets และการกู้คืน RNG/replay/optimizer พร้อมสะพานข้อมูลจำลองจริง ก่อนแช่แข็ง protocol ฝึกใหม่ คงรุ่นตรวจจับ public-v4 และนโยบายเดิมบนเว็บ ตรวจ D1 แบบอ่านอย่างเดียวแล้วตรง release.json ไม่มี deploy หรือการสั่งมอเตอร์จริง


## ฐานตัวเรียน Double DQN และ checkpoint

เพิ่มโครงข่าย 234→64→64→7, masked Double-DQN targets, replay วงแหวน, Adam และ checkpoint ที่เก็บ RNG/online/target/replay/optimizer พร้อม cursor ระหว่าง episode ผ่าน targeted tests Python 18 รายการและ Node 4 รายการตาม protocol ที่แช่แข็งก่อนทดสอบ รายงาน `NAVIGATION_DQN_FOUNDATION_TH.md` และ audit `outputs/Warirak_Navigation_DQN_Foundation_Audit.json` กู้ไฟล์แล้วทำสามขั้นถัดไปได้ actions/samples/loss/tensors ตรงกันใน CPU runtime เดียวกัน

งานปิดแบบ reviewed_component_only, review_complete/delivery_complete=true ใช้เฉพาะข้อมูลและรางวัลสังเคราะห์พร้อม gradient steps จำนวนจำกัดใน unit tests ไม่มี plant rollout, dataset training, validation/test หรือ policy performance การส่ง JSONL ใช้โครงข่ายสุ่มเริ่มต้นและ schema fixture ที่ถูกปฏิเสธโดยค่าเริ่มต้น ไม่มี trained checkpoint ที่เผยแพร่หรือมอเตอร์จริง

ขั้นถัดไปคือ episode/reward/credit driver ที่คง physics/guards/การชนหลัง assistance และการ commit/resume ระหว่าง episode ก่อนแช่แข็ง protocol การฝึกจริง การผ่าน checkpoint ตัวเรียนยังไม่ใช่การกู้ Node plant กลาง episode ตรวจ D1 อ่านอย่างเดียวแล้วยังตรง public-v4 ไม่มี deploy หรือเปลี่ยนนโยบายบนเว็บ


## ตัวเชื่อม episode เครดิตตามเวลา และ journal ผล

เพิ่มตัวเชื่อม R2 ที่บันทึกคำขอเดิมและ issued/applied control ใช้รางวัลเดิม เก็บการชนหลัง STOP/assistance และตรวจผลรวมรางวัล/จำนวนก้าวครบ ผ่าน targeted Node 11 รายการและ Python 9 รายการตาม protocol ที่แช่แข็งก่อน unit steps ไม่ใช่ผลความสามารถนโยบาย ตัวอย่าง snapshot เท่ากับ bare R2 ที่ actuator delay 0/300/600 มิลลิวินาที และไม่ได้ลดกระแสน้ำหรือ noise/gain

เพิ่ม commit ระหว่าง episode ที่ผูก checkpoint/result/cursor/seed และทดสอบ controlled interruption ก่อน/หลัง pointer ทบทวนพบว่าการเก็บ checkpoint สองรุ่นอย่างเดียวไม่พอรักษาผลเก่า จึงเพิ่ม JournaledEpisodeCommitStore และแผนตรวจเพิ่ม 4 รายการโดยไม่รันชุดเดิมซ้ำ ผลราย episode ทั้งห้ายังอยู่เมื่อเหลือ checkpoint สองรุ่น รวม24checks งานปิดแบบ review_complete/delivery_complete แล้ว รายงาน `NAVIGATION_EPISODE_BRIDGE_TH.md` และ audit `outputs/Warirak_Navigation_Episode_Bridge_Audit.json`

ไม่มีการฝึกโมเดลจาก rollout หรือเปิด validation/test ช่วงไม่มีคำขอใหม่สะสมเครดิตแบบหลายก้าวตามคำขอจริงก่อนหน้า ไม่ปลอมเป็น STOP แต่ตัวเรียนเดิมรับเพียง100ms จึงต้องทำ schema/learner ที่รองรับ duration และ gamma^duration ต่อก่อนฝึก ห้ามทิ้งก้าวที่รอหรือการชนหลังขอความช่วยเหลือ การตรวจ commit ยังไม่ใช่ OS hard-kill/ไฟดับหรือกู้ Node กลาง episode ตัวรันจริงต้องใช้ journal wrapper รักษาทุกผล ตรวจ D1 อ่านอย่างเดียวแล้วตรง public-v4 ไม่มี deploy หรือมอเตอร์จริง


## ตัวเรียนเครดิตหลายก้าวตามเวลาจริงในตัวจำลอง

เพิ่ม DurationNavigationDQN/DurationReplayRing และ model/checkpoint/recipe schema ใหม่ โดยไม่เปลี่ยนตัวเรียนหนึ่งก้าวที่แช่แข็ง เป้าหมายใช้ discounted credit กับ gamma^duration ต่อรายการ เก็บเวลา/record/epoch เดิม และตรวจขอบเขตรางวัลสะสมแทนการ clip ที่64 ผ่าน targeted Python 18 รายการ ใช้ bridge software examples ที่บันทึกไว้และกรณีคำนวณสังเคราะห์ ไม่เล่น R2 ซ้ำ ไม่เปิด validation/test และไม่ฝึกจากการเดินเรือ

กู้ไฟล์แล้วทำสามขั้นถัดไปได้ choices/sample/loss/weights/target/Adam/RNG/variable-duration replay ตรงกันใน CPU runtime เดียวกัน และใช้กับ JournaledEpisodeCommitStore ได้ งานปิดแบบ review_complete/delivery_complete แล้ว รายงาน `NAVIGATION_DURATION_LEARNING_TH.md` และ audit `outputs/Warirak_Navigation_Duration_Learner_Audit.json` กรณี960ก้าวเป็นตัวอย่างคำนวณ ไม่ใช่ผล episode960ก้าวที่วัดจริง และ unit gradients ไม่ใช่รอบฝึกโครงงาน

คิวถัดไปเป็น runtime Node/Python เต็มที่ส่ง actor request/duration credit/commit พร้อม schedule ที่กู้ได้และแผนทดสอบ integration แบบจำกัด จากนั้นแช่แข็งงบ snapshots/validation gates/seed registry ก่อนเริ่มรอบฝึกจริง คง physics/guards และผลหลัง STOP/assistance ทุกก้าว ตรวจ D1 อ่านอย่างเดียวแล้วยังตรง public-v4 ไม่มี deployment หรือมอเตอร์จริง
