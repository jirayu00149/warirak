# การแก้ข้อมูลแคชในส่วนบันทึก รุ่น v2

เพิ่ม `ProactiveSidecarV2` ใน `proactive_sidecar_v2.mjs` และตัวหุ้ม `ProactiveSidecarR2V2` ใน `proactive_sidecar_r2_v2.mjs` ใช้ schema `warirak.proactive-sidecar.v2` และ `warirak.proactive-sidecar-r2-step.v2` เพื่อแก้การปฏิเสธข้อมูลแคชที่อาจเกิดขึ้นตามปกติภายใน R2

ซอร์ส v1 และผลทดลองตัวเสนอ v1 ยังตรง hash เดิม การเปลี่ยนส่วนบันทึกไม่ได้เปลี่ยนผล 9 ฉากเก็บสำเร็จ/5 ฉากชนของการทดลองเดิม และยังไม่แก้ปัญหาการเลือกการกระทำในฉากด้านข้าง

## ความหมายของข้อมูลที่เปลี่ยน

เดิมส่วนบันทึกเคยเห็นเฟรมสด sequence 19 ที่เวลา 1900 มิลลิวินาที แต่ได้รับ `cached_wait` sequence 20 ที่เวลาเก็บเดิม 2000 มิลลิวินาที โดยยังไม่เคยอ่านเฟรม 20 ขณะสด เหตุการณ์นี้เกิดได้เมื่อ R2 สร้างเฟรมหลังจบ step แล้วเปลี่ยนมาใช้ cache ก่อนรอบอ่านถัดไป

v2 ยอมเก็บ metadata ของเฟรมแคชที่เพิ่มตามลำดับ เมื่อ schema แหล่งข้อมูล flags เวลา sequence และ payload ระยะถูกต้อง โดยคงเงื่อนไขสำคัญดังนี้

- ค่าระยะสำหรับการตัดสินใจทุกทิศยังเป็น `null` และสถานะเป็น unknown
- `evidence_new.range` ยังเป็น false ใช้ `cached_metadata_advanced` แยกเพื่อบอกเพียงว่า metadata สำหรับตรวจสอบเพิ่มขึ้น
- เวลาเก็บเดิมยังอยู่ครบ ไม่มีการประทับเวลาใหม่ให้ดูสด
- high-water marks เพิ่มตาม metadata เพื่อปฏิเสธข้อมูลที่ย้อนลำดับหรือพยายามเปลี่ยนเฟรมแคชเดิมให้กลายเป็นเฟรมสด
- ข้อมูลต่างกันที่ sequence เดิม ข้อมูลอนาคต เวลา/sequence ถอยหลัง flags ไม่สอดคล้อง หรือ payload ไม่ตรงกันยังถูกปฏิเสธ

ส่วนสรุป features และรูปแบบ issued control ของ R2 ยังคงใช้รุ่นเดิม ส่วนบันทึก v2 ไม่มีตัวเลือกการเดินเรือ ไม่มีการสร้างคำสั่ง และไม่ทำให้ข้อมูลแคชมีสิทธิ์สั่งแรงขับผ่านตัวกำกับ R2

## การตรวจสอบก่อนใช้งานวิจัยต่อ

แผนและซอร์สถูกแช่แข็งก่อนตรวจที่ `work/proactive-sidecar-v2-repair/protocol.json` มี SHA-256 `b0f59a3a608f9a59447f5dc0bc4b29ff2d674d95e0e373e16e7f3710e7171819` การตรวจทั้งหมดผ่าน 40 รายการ ประกอบด้วยข้อกำหนดเดิม 26 รายการที่นำมาตรวจกับ implementation v2 และกรณีเฉพาะการแก้ 14 รายการ

กรณีที่ตรวจรวมถึงลำดับ fresh 19 → cached 20 → fresh 21 ซึ่งนับเฟรมระยะสดได้เพียงสองเฟรม การเริ่ม stream จาก cache ข้อมูลแคชขณะ heading เปลี่ยน ข้อมูลเก่าระหว่างส่ง การห้ามเปลี่ยน cache ให้สด รวมถึงข้อมูลขัดแย้ง/ย้อนเวลา/อนาคต manual/disarm/cancel/ACK/TTL และขอบเขตประวัติ

นำแพ็กเก็ตก่อนเกิดปัญหาที่บันทึกไว้จากทั้งสองตัวควบคุมมาอ่านด้วย v2 แล้วรับ metadata ได้โดยคงระยะเป็น unknown การตรวจนี้เล่นเฉพาะข้อมูลที่มีอยู่ ไม่สร้างหรือเดินตัวจำลอง และไม่ประเมินอัตราเก็บขยะใหม่

มี integration fixture ขนาดเล็กแยกอีกกรณี เพื่อให้ R2 สร้างเฟรมภายในหนึ่ง step แล้วเกิด packet loss ก่อน sidecar อ่าน เปรียบเทียบ snapshot ของ R2 ที่มี/ไม่มีตัวหุ้มแล้วตรงกัน ระหว่างข้อมูลขาดยังมีแรงขับเป็นศูนย์และการลอยตามน้ำ เมื่อเฟรมสดใหม่มาพร้อมคำขอใหม่จึงรับเป็นหลักฐานสดได้

fixture สำหรับทดสอบ parser นี้กำหนด random range dropout เป็นศูนย์เฉพาะเพื่อให้เกิดลำดับเฟรมที่ต้องการก่อนฉีด packet loss อย่างชัดเจน กระแสน้ำยังเป็น 0.08 เมตรต่อวินาที และไม่ได้ใช้กรณีนี้สร้างคะแนนความสำเร็จหรือปรับความยากของการทดลอง v1 ที่ปิดแล้ว

v2 ยังคงเป็นส่วนบันทึกเชิงสังเกต `cancel()` ยกเลิกบริบทการบันทึก ไม่มีการส่ง STOP ไปยังอุปกรณ์ fault ของส่วนบันทึกไม่ควบคุมตัวเรือ การรีเซ็ตยังต้องมีแพ็กเก็ต disarmed ใหม่ที่สด และเก็บ high-water marks เดิม ตัวหุ้มส่งคำขอของผู้เรียกโดยไม่เปลี่ยน R2 ซึ่งยังรักษากระแสน้ำ ความเฉื่อยและตัวกำกับเดิม

## ตรวจฉากสิ่งกีดขวางด้านข้างจากไฟล์เดิม

หลังซ่อมส่วนบันทึก ได้ตรวจหน้าต่างข้อมูลเต็มที่บันทึกไว้ในฉาก `side_circle_current` ตามแผนและ hash แยกใน `work/side-circle-window-inspection` โดยไม่มี rollout การปรับกฎ การฝึก หรือการเปิด validation/test

| ข้อมูลที่ตรวจได้ | ตัวเสนอ v1 | ตัวอ้างอิง |
| --- | ---: | ---: |
| เฟรมที่บันทึกไว้ไม่ซ้ำ | 24 | 12 |
| ช่วง step ที่ครอบคลุมโดยหน้าต่างบางส่วน | 21–82 | 62–73 |
| เฟรมที่สร้าง mask จากประวัติคำขอเดิมได้ | 22 | 11 |
| เฟรมที่ไม่ทราบคำขอก่อนหน้าในหน้าต่าง | 2 | 1 |
| เฟรมระยะสดที่ FORWARD ยังได้รับอนุญาต แต่ขอ STOP | 10 | 0 |

ใน 10 เฟรมของตัวเสนอ v1 นั้น mask เป็น `STOP|FORWARD` และเหตุผลที่บันทึกไว้คือ `no_original_evasive_request_permitted` ตัวเสนอไม่เลือก FORWARD แม้ยังเป็นคำขอที่ตัวกำกับอนุญาต เพราะทางแยกของกฎเน้นการ pivot/HOLD แล้วจบด้วย STOP เมื่อคำขอเหล่านั้นไม่ได้รับอนุญาต

ข้อมูลนี้ช่วยระบุทางแยกของกฎที่ควรศึกษา แต่การที่ FORWARD อยู่ใน mask ไม่รับรองว่าปลอดภัยทุกสถานการณ์ โดยเฉพาะกระแสน้ำผลักเข้าหาผนังยาว ไม่ควรแก้ด้วยการเลือก FORWARD อัตโนมัติทุกครั้งหรือผ่อนระยะตัวกำกับเพื่อให้ฉากที่เห็นผลแล้วผ่าน

หน้าต่างที่มีอยู่ไม่ได้ครอบคลุมทุก step ระหว่าง 21–82 และไม่มีเฟรมต้นทาง step 0–20 จึงยังไม่สร้างประวัติเริ่มต้นหรือระบุเหตุของการตัดสินใจแรกจากการคาดเดา ตัวอ้างอิงและผู้สมัครอยู่คนละตำแหน่ง/เวลาในเส้นทาง จึงไม่ถือว่าตารางนี้เป็นการทดลองแยกผลของปัจจัยเดียว

## งานถัดไปและสถานะเผยแพร่

ส่วนแก้ cache ผ่านการตรวจซอฟต์แวร์เฉพาะจุดแล้ว ขั้นถัดไปคือออกแบบสมมติฐานสำหรับการจัดลำดับคำขอที่ยังได้รับอนุญาต เมื่อ pivot/HOLD ไม่พร้อม โดยต้องพิจารณากรณีสิ่งกีดขวางด้านข้างที่มีขอบเขตและผนังยาวเป็นคู่เปรียบเทียบ กำหนดแผน กรณีทดสอบ และเกณฑ์ก่อนทดลอง ไม่แก้ threshold วนบนฉากเดิม

ยังไม่มีการฝึกหรือนโยบายใหม่ที่อนุมัติใช้งาน ไม่เล่นชุด 14 ฉากเดิมซ้ำเพื่อแก้คะแนน ไม่เปิด validation/test ไม่ deploy เว็บหรือแพ็กชุดดาวน์โหลดใหม่ รุ่นตรวจจับที่อ่านจาก release.json และทะเบียน D1 ยังคงเป็น public-v4 และไม่มีการสั่งมอเตอร์จริง
