# ตัวเชื่อม R2 รางวัล เครดิตตามเวลา และบันทึกผล

ผ่านการตรวจซอฟต์แวร์ใหม่ Node 11 รายการ Python 9 รายการ และส่วนบันทึกผลเพิ่มเติม 4 รายการ รวม 24 รายการ แช่แข็งแผนและ source hash ก่อนแต่ละชุด ไม่ได้ฝึกโมเดลจากการเดินเรือ ไม่เปิด validation/test และไม่เปลี่ยนเว็บหรือต่อมอเตอร์จริง หลักฐานอยู่ที่ `work/navigation-episode-preflight`, `work/navigation-episode-journal-preflight` และ `outputs/Warirak_Navigation_Episode_Bridge_Audit.json`

## ตัวจำลองและข้อมูลของผู้เรียน

`navigation_episode_bridge.mjs` เป็นเจ้าของการ capture → บันทึกคำขอเดิม → step R2 → บันทึก issued/applied control → capture เฟรมถัดไป ใช้ observer, sidecar-v2, encoder และ action mask ที่แช่แข็งไว้ ไม่เปลี่ยนฟิสิกส์ กระแสน้ำ ความเฉื่อย noise/dropout/gain ตัวกำกับ หรือขอบเขต 960 steps ผู้เรียนได้รับเพียง request ที่เข้ารหัสแล้ว ไม่ได้รับ instance ของ driver พิกัดโลก หรือเรขาคณิตจริง

ตรวจ snapshot เทียบกับ R2 เปล่าแบบตรงทุกค่าในตัวอย่างสิบก้าวที่มี actuator delay 0/300/600 มิลลิวินาที ความหน่วงนี้เป็นการส่งคำสั่งไป actuator ในตัวจำลอง แยกจากเวลารอ inference การคำนวณแบบ synchronous บนนาฬิกาจำลองไม่ใช่การวัดความหน่วง Raspberry Pi คำขอใช้เวลาภาพเดิมและ TTL 400 มิลลิวินาที คำตอบที่ถูกยกเลิกหรือถูกแทนที่ไม่สร้างคำขอใหม่ และไม่เปลี่ยนเวลาให้ดูสด

ใช้ฟิกซ์เจอร์เฉพาะสำหรับตรวจซอฟต์แวร์ โดยคงกระแสน้ำและ noise/gain ที่ตัวจำลองสร้างไว้ ตัวอย่างใกล้ตลิ่งกำหนดตำแหน่งเชิงวิเคราะห์เพื่อให้กระแสน้ำเดิมพาไปชนในสี่ก้าว ไม่ใช่ชุดวัดอัตราชนของ AI มี 48 driver steps และ 30 bare-reference steps ในการตรวจนี้ ไม่ได้ประเมินนโยบายเต็มสนามหรือวัดอัตราสำเร็จ การคงขอบเขต 960 steps ไม่ใช่หลักฐานว่าชุดนี้ได้เล่นครบ 960 steps

## รางวัลและช่วงที่ไม่มีคำขอใหม่

รางวัลยังเป็น 3×ระยะที่เข้าใกล้เป้าหมาย −0.015 ต่อ step +40 เมื่อเก็บได้ −30 เมื่อชน −10 เมื่อเข้าสู่ assistance ครั้งแรก ใช้พิกัดโลกเฉพาะรางวัลและผลปลายทาง ไม่ใช่ actor input ตัวอย่าง STOP ใช้แรงขับที่ส่งจริงเป็นศูนย์ แต่กระแสน้ำยังทำให้ชนได้ อีกตัวอย่างขอความช่วยเหลือแล้วคำนวณต่อจนชน โดยคิด assistance เพียงครั้งเดียวและยังเก็บค่าปรับการชนครบ

เมื่อไม่มีคำขอใหม่ ไม่บันทึกว่าได้ส่ง STOP แทน คำขอจริงก่อนหน้าจะสะสมรางวัลในช่วงรอ พร้อม `duration_steps`, ผลรวมรางวัลดิบ และผลรวมรางวัลลดค่าตามเวลา `Σ gamma^k × reward_k` ค่าต่อเนื่องเป็น `gamma^duration_steps` หากมีช่วง passive ก่อนคำขอแรก จะเก็บจำนวนก้าวและรางวัลไว้แยกอย่างชัดเจน เพราะยังไม่มี action ที่นำไปให้เครดิตได้ ผลของ episode ยังคงรวมช่วงนั้น

ตรวจทั้งผลรวมรางวัลดิบและจำนวนก้าวให้เท่ากับทุกก้าวของโลกจริงในตัวจำลอง การเปลี่ยน epoch ล้างประวัติของ actor แต่ไม่ตัด episode หรือรางวัลทิ้ง เฉพาะ collection, collision และ time limit เต็มเท่านั้นเป็น terminal

ตัวเรียน Double DQN รุ่นก่อนรับ transition ทีละ 100 มิลลิวินาทีเท่านั้น `durationCreditToOneStep` จึงปฏิเสธเครดิตหลายก้าวอย่างชัดเจน ไม่แบ่งเครดิตด้วยเวลาปลอม ไม่ทิ้งก้าวที่รอ และไม่สร้าง action ที่ไม่เคยส่ง ต้องเพิ่มตัวเรียนที่รองรับระยะเวลาและ discount ต่อ transition ก่อนฝึกงานที่มีช่วงขาดคำขอจริง

## Commit และการรักษาผลทุก episode

`navigation_commit.py` เขียน checkpoint, ผล และ manifest ให้ครบก่อนแทน pointer `CURRENT.json` ชุดเดียว เมื่อเกิด controlled interruption ก่อนเปลี่ยน pointer จะกู้ชุดเก่าที่ครบ เมื่อเกิดหลังเปลี่ยน pointer จะกู้ชุดใหม่ที่ครบ ตรวจ seed ต่อเนื่อง cursor, ผลปลายทางหนึ่งประเภท และเครดิตที่ปิดครบ ไม่ข้าม seed หรือย้ายไฟล์ orphan มาเป็นผลที่ commit แล้วเอง

การทบทวนพบว่าเก็บ checkpoint ย้อนหลังสองรุ่นเพียงอย่างเดียวจะทำผลเก่าหายไปด้วย จึงเพิ่ม `JournaledEpisodeCommitStore` ใน `navigation_commit_journal.py` เป็น wrapper ใหม่ โดยเก็บผลและ manifest ราย episode พร้อม hash chain แยกไว้ก่อนล้าง generation เก่า ตรวจเพิ่มสี่กรณีโดยไม่รันชุดเดิมซ้ำ ทดสอบห้าผลแล้วเหลือ checkpoint สองรุ่น แต่ผลทั้งห้ายังตรวจกลับได้ครบ ตัวรันจริงในอนาคตต้องใช้ wrapper นี้ ไม่ใช้ base store เพียงลำพัง

Journal จำกัด 64 MiB ผลหนึ่ง episode ไม่เกิน 8 KiB และ receipt ไม่เกิน 16 KiB ไม่มีการล้าง journal ของผลที่ commit แล้ว การล้าง checkpoint เก่าตรวจชื่อ path ที่ resolve อยู่ในโฟลเดอร์เฉพาะ hash และรายชื่อไฟล์ก่อนลบทีละไฟล์ ไม่ใช้ recursive delete ไฟล์ orphan และ pending เก็บไว้พร้อมขีดจำกัดเพื่อรอทบทวน ห้ามอ้างว่าเติมประวัติที่หายจาก run เก่าซึ่งไม่ได้ใช้ journal กลับมาได้

ผลตรวจการขัดข้องเป็นการโยน exception ณ จุด transaction ที่กำหนด ไม่ใช่ OS hard kill หรือความทนทานต่อไฟดับ ยังไม่รองรับการกู้ Node plant กลาง episode หากมี process lock ค้าง ต้องตรวจเจ้าของ process และ checkpoint ก่อนดำเนินการต่อ ไม่มีการลบ lock โดยอัตโนมัติ

## ขั้นถัดไป

ทำ learner/checkpoint schema ใหม่ที่รับ duration credit และใช้ discount ต่อรายการ พร้อม masked targets, terminal และการกู้ replay/RNG/Adam โดยใช้ตัวอย่างที่บันทึกแล้วเพื่อไม่เล่นชุดตรวจนี้ซ้ำ จากนั้นทำตัวรัน Python/Node และแผนฝึกฉบับเต็มที่กำหนดงบ schedule, snapshots, validation-only gates และ seed/exposure registry ก่อนเริ่มงานจริง

รุ่นตรวจจับยังเป็น public-v4-2026-10-28 ตรงกันระหว่าง release.json กับ D1 ที่อ่านอย่างเดียว ไม่มีการเปลี่ยนนโยบายห้าคำขอบนเว็บ ผล unit tests นี้ไม่ใช่ความแม่นยำในการตรวจจับขยะ ผลการขับเรือภาคสนาม หรือการอนุมัติใช้งานจริง
